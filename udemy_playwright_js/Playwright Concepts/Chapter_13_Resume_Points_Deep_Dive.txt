13.1 PAGE OBJECT MODEL (POM) DESIGN PATTERN
----------------------------------------------------------------

What: A design pattern where each web page has its own class.
Why: Keeps locators and actions separate from test logic. If UI changes, you fix one file.

Structure:
  pageobjects/
  ├── LoginPage.js
  ├── DashboardPage.js
  ├── CartPage.js
  └── OrderSummaryPage.js

Code (LoginPage.js):
  class LoginPage {
      constructor(page) {
          this.page = page;
          this.userName = page.locator("[formcontrolname='userEmail']");
          this.password = page.locator("#userPassword");
          this.signInBtn = page.locator("#login");
      }

      async goTo() {
          await this.page.goto("https://example.com/client");
      }

      async validLogin(username, password) {
          await this.userName.fill(username);
          await this.password.fill(password);
          await this.signInBtn.click();
      }
  }
  module.exports = { LoginPage };

Code (Test file):
  const { LoginPage } = require('../pageobjects/LoginPage');

  test('login test', async ({ page }) => {
      const loginPage = new LoginPage(page);
      await loginPage.goTo();
      await loginPage.validLogin("user@mail.com", "Pass123");
  });

Interview tip: "I implemented POM to separate page-specific locators
and actions into dedicated classes, making tests readable and
maintenance easy when UI changes."

13.2 ROLE-BASED LOCATORS (ACCESSIBILITY-FIRST)
----------------------------------------------------------------

What: Playwright's recommended locators that target elements by their accessibility role.
Why: More resilient to DOM changes than CSS selectors. IDs/classes change, roles rarely do.

Code:
  page.getByRole('button', { name: 'Login' })        // <button>Login</button>
  page.getByRole('link', { name: 'Shop' })            // <a>Shop</a>
  page.getByRole('heading', { name: 'Dashboard' })    // <h1>Dashboard</h1>
  page.getByTestId('submit-btn')                      // [data-testid="submit-btn"]
  page.getByLabel('Username')                         // Input with <label>Username</label>
  page.getByPlaceholder('Enter email')                // Input with placeholder
  page.getByText('Welcome back')                      // Element with visible text

Interview tip: "I used role-based locators as my primary strategy because
they're accessibility-compliant and don't break when developers change
class names or IDs."

13.3 AUTO-WAIT MECHANISM
----------------------------------------------------------------

What: Playwright automatically waits for elements to be actionable before performing actions.
Why: Eliminates the need for Thread.sleep() or explicit waits (unlike Selenium).

What Playwright waits for before .click():
  - Element is visible
  - Element is stable (not animating)
  - Element is enabled
  - Element is not obscured by another element

Code:
  // NO explicit waits needed — Playwright handles it internally
  await page.locator('#submit').click();  // Waits until clickable automatically

  // In Selenium you'd need:
  // WebDriverWait wait = new WebDriverWait(driver, 10);
  // wait.until(ExpectedConditions.elementToBeClickable(By.id("submit")));

Interview tip: "Playwright's auto-wait eliminated flaky tests caused by
timing issues. I rarely needed explicit waits because actions automatically
retry until the element is actionable."

13.4 CUSTOM FIXTURES
----------------------------------------------------------------

What: Extend Playwright's test function with reusable preconditions.
Why: Avoids repeating setup code (login, create profile) across tests.

Code (test-base.js):
  const { test: base } = require('@playwright/test');

  exports.test = base.extend({
      authenticatedPage: async ({ browser }, use) => {
          const context = await browser.newContext({
              storageState: 'auth.json'
          });
          const page = await context.newPage();
          await use(page);
          await context.close();
      },
      testData: {
          username: "user@mail.com",
          password: "Pass123",
          product: "ZARA COAT 3"
      }
  });

Code (test file):
  const { test } = require('../utils/test-base');

  test('dashboard test', async ({ authenticatedPage }) => {
      await authenticatedPage.goto('/dashboard');
      // Already logged in — no login step needed!
  });

Interview tip: "I created custom fixtures for authenticated user sessions
and child profile setup, reducing code duplication across 100+ tests."

13.5 TEST HOOKS (LIFECYCLE MANAGEMENT)
----------------------------------------------------------------

What: Functions that run before/after tests for setup and cleanup.
Why: DRY principle — don't repeat login/cleanup in every test.

Code:
  test.beforeAll(async () => {
      // Runs ONCE before all tests in the file
      // Good for: API login, database seeding
  });

  test.beforeEach(async ({ page }) => {
      // Runs before EACH test
      // Good for: Navigate to starting page
      await page.goto('https://example.com');
  });

  test.afterEach(async ({ page }) => {
      // Runs after EACH test
      // Good for: Clear data, logout
  });

  test.afterAll(async () => {
      // Runs ONCE after all tests
      // Good for: Close connections, cleanup
  });

13.6 NETWORK INTERCEPTION & API MOCKING (page.route)
----------------------------------------------------------------

What: Intercept network requests and modify/mock responses.
Why: Test edge cases (errors, empty states, slow loading) without depending on real backend.

Code — Mock an API response:
  await page.route('**/api/products', route => {
      route.fulfill({
          status: 200,
          contentType: 'application/json',
          body: JSON.stringify([{ name: 'Mock Product', price: 100 }])
      });
  });
  await page.goto('/products');
  // Page shows "Mock Product" — no real API call made

Code — Simulate server error:
  await page.route('**/api/orders', route => {
      route.fulfill({ status: 500, body: 'Internal Server Error' });
  });
  // Test how UI handles a 500 error

Code — Block images (speed up tests):
  await page.route('**/*.{png,jpg,jpeg}', route => route.abort());

Interview tip: "I used network interception to mock API failures and
edge cases that are difficult to reproduce with real servers, like
500 errors and empty product lists."

13.7 API TESTING WITH PLAYWRIGHT REQUEST FIXTURE
----------------------------------------------------------------

What: Built-in HTTP client — no need for Postman/Axios in test code.
Why: Validate APIs directly in the same test framework, combine UI + API testing.

Code:
  const { test, expect, request } = require('@playwright/test');

  test.beforeAll(async () => {
      const apiContext = await request.newContext();

      // POST - Login
      const response = await apiContext.post('https://api.example.com/auth/login', {
          data: { email: 'user@mail.com', password: 'Pass123' }
      });
      expect(response.ok()).toBeTruthy();
      const json = await response.json();
      console.log(json.token);

      // GET - Fetch products
      const products = await apiContext.get('https://api.example.com/products');
      expect(products.status()).toBe(200);

      // PUT - Update profile
      const update = await apiContext.put('https://api.example.com/profile', {
          data: { name: 'New Name' },
          headers: { 'Authorization': json.token }
      });

      // DELETE - Remove item
      const del = await apiContext.delete('https://api.example.com/cart/item123', {
          headers: { 'Authorization': json.token }
      });
  });

Interview tip: "I used Playwright's built-in request fixture for API
testing — login via API, inject token into browser, then run UI tests.
This eliminated UI login overhead and made tests 3x faster."

13.8 TOKEN INJECTION (API LOGIN + UI TESTING)
----------------------------------------------------------------

What: Login via API, get token, inject into browser localStorage, skip UI login.
Why: Faster tests — API login takes 200ms vs UI login taking 3-5 seconds.

Code:
  test.beforeAll(async () => {
      const apiContext = await request.newContext();
      const response = await apiContext.post('/api/auth/login', {
          data: { email: 'user@mail.com', password: 'Pass123' }
      });
      const { token } = await response.json();
      // Store token for later use
  });

  test('dashboard', async ({ page }) => {
      // Inject token into localStorage BEFORE navigating
      await page.addInitScript(value => {
          window.localStorage.setItem('token', value);
      }, token);

      await page.goto('/dashboard');
      // You're logged in! No UI login needed.
  });

Interview tip: "I combined API and UI testing by logging in via API,
extracting the JWT token, and injecting it into browser localStorage
using addInitScript. This bypassed UI login for 80% of tests."

13.9 CROSS-BROWSER TESTING (PROJECTS)
----------------------------------------------------------------

What: Run the same tests across Chromium, Firefox, and WebKit from one config.
Why: Ensure app works across all browsers without maintaining separate test suites.

Code (playwright.config.js):
  projects: [
      { name: 'chromium', use: { browserName: 'chromium' } },
      { name: 'firefox', use: { browserName: 'firefox' } },
      { name: 'webkit', use: { browserName: 'webkit' } },
  ]

Run:
  npx playwright test                        # All browsers
  npx playwright test --project=chromium     # Just Chrome

Interview tip: "I configured cross-browser testing as projects in the
config. One codebase, three browsers, parallel execution."

      ...devices['iPhone 13'],

What trace shows:
  - DOM snapshot at each step
  - Network requests and responses
  - Console logs
  - Screenshots at each action
  - Timing information

13.18 SOFT ASSERTIONS (expect.soft)
----------------------------------------------------------------

What: Assertions that don't stop test execution on failure.
Why: Collect multiple failures in one test run instead of stopping at the first.

Code:
  await expect.soft(page.locator('.currency')).toHaveText('$');    // Non-critical
  await expect.soft(page.locator('.format')).toHaveText('USD');    // Non-critical
  await expect(page.locator('.total')).toHaveText('$99.99');       // Critical — stops on fail

Interview tip: "I used soft assertions for cosmetic checks (formatting,
currency symbols) and hard assertions for critical business logic."

13.25 JENKINS CI/CD INTEGRATION
----------------------------------------------------------------

What: Automate test execution on code commits or schedules.
Why: Catch bugs early, ensure quality gates before deployment.

Jenkinsfile:
  pipeline {
      agent any
      triggers { cron('H 2 * * *') }
      stages {
          stage('Install') { steps { sh 'npm ci' } }
          stage('Test')    { steps { sh 'npx playwright test' } }
          stage('Report')  { steps { sh 'npx allure generate ./allure-results' } }
      }
      post {
          always { archiveArtifacts 'playwright-report/**' }
          failure { mail to: 'team@company.com', subject: 'Tests Failed' }
      }
  }
