Q3: "Explain auto-wait in Playwright. How is it different from Selenium?"
----------------------------------------------------------------

ANSWER:
"Playwright's auto-wait is built into every action — click, fill, type,
check. Before performing any action, Playwright automatically verifies:
- Element is attached to DOM
- Element is visible
- Element is stable (not animating)
- Element is enabled
- Element is not obscured

In Selenium, you'd write explicit waits for every interaction:
  WebDriverWait wait = new WebDriverWait(driver, 10);
  wait.until(ExpectedConditions.elementToBeClickable(By.id('btn')));
  driver.findElement(By.id('btn')).click();

In Playwright, it's just:
  await page.locator('#btn').click();  // Waits automatically

This eliminated 90% of timing-related flakiness in my test suite and
made tests about 40% shorter in terms of code lines."

Q4: "How do you handle authentication in your tests?"
----------------------------------------------------------------

ANSWER:
"I use a two-strategy approach depending on the scenario:

Strategy 1 — API login + token injection (for most tests):
  - Call login API in test.beforeAll → get JWT token (200ms).
  - Use page.addInitScript() to inject token into localStorage.
  - Navigate to app → already authenticated.
  - 10x faster than UI login per test.

Strategy 2 — storageState (for session-based auth):
  - Login via UI once in a setup project.
  - Save cookies/localStorage to auth.json via context.storageState().
  - All subsequent tests load auth.json — skip login entirely.

I keep 2-3 dedicated UI login tests to validate the actual login flow,
but the remaining 97% use API shortcut for speed."

Q5: "How do you handle flaky tests?"
----------------------------------------------------------------

ANSWER:
"My approach to flakiness is layered:

1. Prevention (design):
   - Auto-wait handles most timing issues.
   - Role-based locators (getByRole) resist DOM changes.
   - Test isolation — each test creates its own data.

2. Detection:
   - Playwright's retry mechanism (retries: 2 in config).
   - Allure reports track flaky tests over time.
   - Mark tests with test.fixme() while investigating.

3. Debugging:
   - Trace Viewer — DOM snapshots, network, console at each step.
   - video: 'retain-on-failure' — see exactly what happened.
   - waitForResponse() for API-dependent elements.

4. Resolution:
   - Replace brittle locators with resilient ones.
   - Add waitFor() for dynamically loaded content.
   - Use network interception to control timing for edge cases.

This reduced our flaky rate from 15% to under 2%."


----------------------------------------------------------------
Q6: "Explain network interception in Playwright."
----------------------------------------------------------------

ANSWER:
"page.route() intercepts HTTP requests before they reach the server.
I use it for three purposes:

1. Mock API responses (test edge cases):
   await page.route('**/api/profiles', route => {
       route.fulfill({ status: 200, body: JSON.stringify([]) });
   });
   → Tests empty state without deleting real data.

2. Simulate errors:
   await page.route('**/api/orders', route => {
       route.fulfill({ status: 500, body: 'Server Error' });
   });
   → Tests error handling UI without breaking real servers.

3. Speed up tests:
   await page.route('**/*.{png,jpg}', route => route.abort());
   → Blocks images/analytics — tests run 30% faster.

In my project, this gave me 100% coverage of error scenarios that would
be impossible to reproduce on real environments."

Q7: "How do you do cross-browser testing?"
----------------------------------------------------------------

ANSWER:
"Playwright supports Chromium, Firefox, and WebKit from a single codebase.
I configure them as projects in playwright.config.js:

  projects: [
      { name: 'chromium', use: { browserName: 'chromium' } },
      { name: 'firefox', use: { browserName: 'firefox' } },
      { name: 'webkit', use: { browserName: 'webkit' } },
  ]

Same test code runs against all three browsers in parallel. No separate
drivers, no separate configs.

I can run selectively too:
  npx playwright test --project=chromium

This caught 3-4 browser-specific bugs per release — mainly CSS rendering
differences in Safari and dropdown behavior in Firefox."

Q9: "How do you debug a failing test?"
----------------------------------------------------------------

ANSWER:
"My debugging workflow:

1. Check the error message and stack trace — usually tells me the line.

2. Check the HTML report — auto-attached screenshot shows the page state.

3. Trace Viewer (npx playwright show-trace):
   - See DOM snapshot at the exact step that failed.
   - Inspect network requests (did the API return expected data?).
   - Check console logs for JavaScript errors.
   - See timing between steps.

4. Run headed with slowMo:
   npx playwright test --headed
   → Watch the test execute in real-time.

5. page.pause() for interactive debugging:
   → Freezes execution, opens Playwright Inspector.
   → Try locators, step through actions.

6. If it's a timing issue: check if waitFor() or waitForResponse() is needed.

7. If it's a locator issue: check if the DOM changed — update the locator."

Q10: "Explain Page Object Model in Playwright."
----------------------------------------------------------------

ANSWER:
"POM separates page-specific logic from test logic.

Structure:
  // LoginPage.js
  class LoginPage {
      constructor(page) {
          this.page = page;
          this.email = page.getByPlaceholder('Email');
          this.password = page.locator('#password');
          this.submitBtn = page.getByRole('button', { name: 'Login' });
      }

      async goTo() { await this.page.goto('/login'); }

      async login(email, password) {
          await this.email.fill(email);
          await this.password.fill(password);
          await this.submitBtn.click();
      }
  }

  // Test file
  test('login test', async ({ page }) => {
      const loginPage = new LoginPage(page);
      await loginPage.goTo();
      await loginPage.login('user@mail.com', 'Pass123');
  });

Benefits:
- If the email field's locator changes → update ONE file, not 50 tests.
- Tests read like English: loginPage.login() → dashboardPage.addToCart()
- New team members understand the flow instantly.
- Code reviews are faster — tests are concise."


----------------------------------------------------------------
Q11: "What locator strategy do you recommend?"
----------------------------------------------------------------

ANSWER:
"My priority order:
1. getByRole — most resilient, accessibility-compliant
2. getByTestId — stable if developers maintain data-testid attributes
3. getByLabel/getByPlaceholder — for form fields
4. CSS selectors — fallback for complex elements
5. XPath — last resort, only when traversing up the DOM

I avoid:
- Indexes (nth) when filter can identify the element.
- Class-based selectors alone (classes change with styling).
- Auto-generated locators without review.

In my project, switching from CSS to getByRole reduced test breakage
during UI redesigns by 80%."

Q13: "Explain async/await in JavaScript."
----------------------------------------------------------------

ANSWER:
"async/await is JavaScript's way of handling asynchronous operations
in a readable, synchronous-looking way.

- 'async' marks a function as asynchronous — it returns a Promise.
- 'await' pauses execution until the Promise resolves.

Without await:
  const text = locator.textContent();  // Promise { <pending> }

With await:
  const text = await locator.textContent();  // 'Actual text'

In Playwright, almost every interaction is async because it communicates
with the browser. That's why nearly every Playwright method needs await."


----------------------------------------------------------------
Q14: "What CSS selectors do you use for locating elements?"
----------------------------------------------------------------

ANSWER:
  #id                    → Element with specific ID
  .class                 → Element with specific class
  tag.class              → Specific tag with class: input.form-control
  [attribute='value']    → Attribute match: [name='email']
  [attr*='partial']      → Contains: [href*='login']
  parent child           → Descendant: .form input
  parent > child         → Direct child: ul > li
  :nth-child(2)          → Second child element
  :first-child, :last-child → First/last

"I understand CSS deeply because Playwright's locator engine uses it
as one of its primary selector strategies."


----------------------------------------------------------------
Q15: "Explain the difference between let, const, and var."
----------------------------------------------------------------

ANSWER:
  const → Cannot be reassigned. Use for locators, URLs, fixed values.
  let   → Can be reassigned. Use for counters, accumulated values.
  var   → Old style. Function-scoped (not block-scoped). Avoid it.

  const page = await context.newPage();  // Never reassigned → const
  let count = 0;                         // Will increment → let
  count++;                               // ✅ works with let

"In my automation code, I use const for 95% of variables. Only let for
loop counters or values that genuinely need to change."
